Q1. You schedule a cron job as */5 * * * * bash ~/scripts/cleanup.sh. The script works perfectly when you run it manually, but the cron job silently does nothing. What's the most likely category of problem, and how would you start debugging it?

Its a file path problem.~ is a shell shorcut for specific users home directory.this will exapnd into bash home/username/scripts/cleanup.sh when you manually run this in an interactive shell.But cron uses /bin/sh (standard POSIX shell) so it will read ~ as just a directory name in path and throw an error no such file or directory.
You can start debugging by checking syslog.(grep CRON /var/log/syslog) but you will have to search through every other log.The best practice is to always log cron jobs output to a custom file.Because cron runs in background it wont print any error messages to a terminal.You can do this when sheduling the cron job in first place by */5 * * * * bash /home/username/cleanup.sh >> /home/username/cleanup_cron_log.log 2>&1 

Q2. What's the difference between editing your crontab with crontab -e and manually placing a file in /etc/cron.d/? When would you choose one over the other?

crontab -e is designed for individual users managing their own task./etc/cron.d/ is a system directory is used for system wide automations.Its used by system admins and software packages.there a many differences between them.
*Syntax 
crontab -e = 5 time fields + command
cron.d = 5 time fields + username + command

*permission
crontab -e = any user can create,edit or delete their own jobs
cron.d = requires root access to create or edit files

*validation
crontab -e = checks for syntax error upon saving
cron.d = No syntax checking because you are just creating or placing a file inside a directory.It will fail if there are any typos.

*storage location
crontab -e = /var/spool/cron/crontabs/
cron.d = /etc/cron.d/

crontab is best for personal task automations.(backup files, manage log files, pull data from API)
cron.d is best for production system building,server setups.(CI and CDs, IaS)

the error might be in the file path.because HOME is inside the script and it will correctly interpretted as /home/username.This variable even work at crontab itself because when cron triggers a script it automatically sets basic set of enviorenment variables.Including HOME, USER and SHELL.what could happen is there are other paths that doesnt have $PATH or full path.
the shell env is interactive and cron isnt.
shell uses modern,feature rich shell binaries (/bin/bash, /bin/zsh) while cron uses minimal POSIX binaries(/bin/sh)
shell automatically loads configuration files but cron completely ignores them.
In shell you can use both relative and absolute paths including shortcuts as ~.But cron only supports absolute paths.
