Q6. Your ~/.ssh/ directory has these permissions: drwxrwxrwx. Everything inside it has chmod 600. SSH still refuses your key. You already know from Q2 that SSH checks the key file — but what else does it check, and why?

Local directory and configurations - ssh checks the permission of your .ssh directory and config files.If the directory is writable to anyone else but you they can inject malicious config files.If the config file is writable anyone who has the access can they can edit your config files to redirect your traffic to another server.

Remote servers identity - ssh lools up the servers public host key inside your local .ssh/known_hosts file.If thhe host key has changed since the last connection ssh refuses to connect.Because the server could be an attacker impersonating as your server.

Server side file permissions - when your key reached to the server ssh daemon validated the destination enviorenment.If the permission are loose server ignores the key and fallback to password auth.The remote home directory, remote .ssh forlder and authorized keys file must not be world writable.If these are world writable anyone can edit the .ssh directory and configuration files inside it.

Server configurations - The remote server checks your login attempt against its global security policies.AllowUsers / DenyUsers are the servers whitelist and blacklist.If your username isnt explicitly allowed you are blocked.PermitRootLogin checks if you are trying to login directly as root.If this is set to yes you can connect but almost always its set to no.The client and server negotiate encryption algorithms and key exchange methods to find a method they both support.If nothing matches connection fails.

Network and Firewall safeguards - Server checks your local IP address is explicitly allowed or blocked.If your IP address previously triggered multiple failed login attempts the servers firewall drop your connection before ssh evaluate keys.This happens if Fail2ban or IP rate limiting is configured in firewall.

Q10. You run ssh user@server and get this warning:



@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@ WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED! @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Most people google "how to fix this" and blindly remove the old key from known_hosts. But what is SSH actually telling you? In what scenario is this warning protecting you from a real attack vs. just a harmless server rebuild?

when you log into a remote server for the first time a cryptographic fingerprint is stored in both server and the local machine.The next time you connect to the server ssh compare the local fingerprint against servers fingerprint.If they dont match ssh throw this error and refuce to connect.There are multiple ways that could change this fingerprint.
Reinstalled OS - If the person/service who manage the server rebuilt or reinstall the server it will automatically generate new host keys.
IP address reuse - Imagine you launce an instance from a cloud provider and ssh into that server and do whatever you do and terminate the instance.By doing this your local machine stores a fingerprint that belongs to the server at that IP address.Then cloud provider mark as that IP address is available to use.Then someone else launch an instance and provider assign that ip address to that machine.They finish their work and terminate it.Then you launch a instance again and provider assign that ip address again to your server.When you ssh into that server your local machine already has a fingerprint on that ip address.But the servers fingerprint has changed because it was rebuilt.So ssh throw this error.
Upgraded SSH - If the server upgraded its OpenSSH daemon it will change its default host key algorithm.

If you are not in none of above situations its protecting you agains actual threat or attack.If you are using public wifi this could be a real attack.If the server has been running for long time and suddenly this error pop up this could be an attack.If the server uses a static IP address this error can protect you from an attack.The server has not upgraded its SSHd this could protect you from an attack
