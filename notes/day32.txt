Q2. In a multi-stage Dockerfile, you write COPY --from=builder /app/server . — but builder doesn't exist as a container on your system. How does Docker know what builder refers to?

when docker reads your docker file it create an interconnected node chain(dependancy graph) that each connects to the next node that start from 0.Each node is one instruction line in your dockerfile.The instructions that start with FROM becomes the first node (node 0)of a chain.'As builder' is an alias(stage aliase) to a node that fall though the chain.Which means when docker reads the From golang:1.21. As builder docker creates an aliase to the first node in docker buildKit's temporary build graph.(this is created in that process' memory space.which means docker buildKit's memory space.)When docker read the next line the aliase's pointer move to the next node.This happens untill docker reads next FROM line.Which means the start of a new node chain.So now aliase is point to the last node of the first stage.Then docker read the next stage same as before chaining each node and creating build graph.while reading the file docker hits the copy --form=builder /app/server . builder aliase already has a pointer to the last node of the stage one.so now both chains are connected.After creating the graph built Kit start executing all the chains parellaly.Which means All FROM instructions are executed at the same time.But in the stage 2 in the copy node it has two parent nodes.So it wait for both nodes to finish their execution and copy the files.

the builder act as a bridge between 2 chains.Docker knows what builder refers to because it was written as an aliase to the last node of the stage one in directed acyclic graph in docker buildKit's memory space.

Q6. Your multi-stage build uses FROM golang:1.21-alpine AS builder and later FROM alpine:3.19. You change app.go and rebuild. Does Docker re-run the FROM alpine:3.19 stage or use cache? What determines this?

It will re run the second stage.Unless you rebuild the image seperately.assuming the rebuild is done by the same muti-stage build;
when you change your code the layer cache break on the first stage when building the image.which means builder aliase is now pointing to different image id.So when the second stage runs it does not pull from the same files.So it will rerun the second stage.But this will not break the stage 2 base layer because it has not changed.So every layer after that will be re written.

Docker buildKit computes a cryptographic hash of the actual files being copied from builder stage.Becasue code changed your code inside the builder image has changed.So it gets a new hash.So docker invalidates the cache on this COPY instruction and copy the files again.Thats called cache miss.Its what determines the use cached image or rebuild.

Q8. What's wrong with this multi-stage Dockerfile?

dockerfile


FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY app.go .
RUN go build -o server app.go
FROM scratch
WORKDIR /app
COPY --from=builder /app/server .
EXPOSE 8080
CMD ["./server"]
It builds fine, but when you run it with a health check using curl, it fails. Why?

When you build a image FROM scratch it does not have an underlying OS layer.It start from 0 bytes.Since it does not have an OS it does not have default OS services and libraries.So no shell inside the container and no shell tools like curl, ls.The app still run because it need zero third party dependencies.Because go compile statiaclly compiled binaries.But the curl fail because container does not know what curl is and has no shell to run it.
